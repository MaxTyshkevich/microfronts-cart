# Архитектура Cart

## Ответственность и текущая реализация

Cart показывает корзину и изменяет количество товаров. Работает standalone и как cart/CartApp внутри Shell.

- src/main.tsx — standalone bootstrap: React root, собственный QueryClient, runtime config и гостевой ключ.
- src/CartApp.tsx — exposed component и текущая композиция загрузки корзины и мутаций.
- src/models.ts — модели Cart и CartItem.
- src/api.ts — HTTP helper и форматирование денежных сумм.
- src/cart-key.ts — гостевой ключ для standalone.
- src/app/styles/tailwind.css — собственные Tailwind utilities и тема без reset.
- src/app/styles/remote.css — оставшиеся стили remote; src/app/styles/standalone.css — обрамление standalone.

Запросы и мутации корзины принадлежат Cart. Ключ кеша берётся из contracts и учитывает контекст корзины; после успешной мутации запрос инвалидируется. refreshVersion поддерживается для совместимости с host.
В host используется переданный QueryClient. Standalone работает без Shell; без sessionScope HTTP helper не отправляет cookies. Ошибки 401/410 передаются через onUnauthorized, когда callback задан. createRoot вызывается только standalone-точкой входа.

## FSD

Обязательный стандарт развития — [Feature-Sliced Design](https://fsd.how/docs/get-started/overview/).
Исходники пока расположены преимущественно прямо в src; это текущее отклонение от стандарта, а не завершённая FSD-структура.

Порядок слоёв: app → pages → widgets (при обоснованной необходимости) → features → entities → shared.
Использовать только нужные слои; устаревший processes не создавать. По текущим рекомендациям FSD widgets обычно не нужен: композицию размещать в странице или layout приложения.

- app: запуск, провайдеры, глобальные стили, маршрутизация и интеграционные адаптеры.
- pages: страницы и их локальная логика.
- features: переиспользуемые пользовательские действия.
- entities: модели, API и представления бизнес-сущностей.
- shared: инфраструктура и общие утилиты без бизнес-логики.

В pages/features/entities (и widgets, если он необходим) сначала выделять предметный слайс, затем сегменты ui/model/api/lib/config по необходимости. app и shared делить непосредственно на сегменты.

Импорты между слоями направлены строго вниз; слайсы одного слоя изолированы. Внешние потребители слайса обращаются к его публичному API (например, index.ts), без глубоких импортов. Внутренние импорты самого слайса допустимы. Контролируемые связи entities через @x допустимы только с явным обоснованием здесь. Межрепозиторные зависимости поставляются опубликованными пакетами/архивами или контрактом Module Federation, а не импортом соседних исходников.

Новый код следует этим правилам. Legacy-код переносится в пределах затронутой ответственности, сохраняя публичные exposed modules, standalone-запуск и поведение. Массовая миграция выполняется отдельной задачей; таблица ниже — направление миграции, а не перечень уже созданных каталогов.

| Ответственность | Размещение при миграции |
| --- | --- |
| Standalone bootstrap, providers и адаптер exposed module | app |
| Экран корзины, композиция и локальная логика страницы | pages/cart |
| Переиспользуемый сценарий изменения количества | features/change-cart-item |
| Cart/CartItem, запросы, ключи и представления сущностей | entities/cart |
| Низкоуровневый HTTP и форматирование денег | shared/api, shared/lib |

Правила корзины остаются в предметных слоях. HTTP helper при переносе отделяется от привязки к сессии/корзине.

## Общие зависимости и интеграция

React 19, TypeScript, Vite и Module Federation. Серверное состояние управляется TanStack Query.
UI и типы интеграции поставляются архивами @microfronts/ui и @microfronts/contracts в vendor; архивы и package-lock.json хранятся в Git. src/remote-props.ts реэкспортирует типы contracts. Изменения контракта требуют согласованного обновления потребителей.

Связь host и remote: props apiBaseUrl, cartKey, queryClient, sessionScope и callbacks onUnauthorized/onNavigate. Shell владеет маршрутизацией и общим QueryClient, remote владеют своей бизнес-логикой и запросами. Исходники соседних приложений не импортируются. Общий event bus и пакет platform приложениями не используются.

## Конфигурация и проверки

Настройки окружения перечислены в [.env.example](../.env.example), команды запуска — в [README](../README.md).
runtime-config.json формируется инфраструктурой сборки/запуска; секреты в браузерную конфигурацию не помещаются.
Для локальной проверки кода: npm run typecheck и npm run build:local. npm run build предназначен для production с HTTPS-настройками. Существующий CI выполняет установку, проверку типов и production-сборку.
Интеграционный стенд и E2E находятся в отдельном репозитории integration общего workspace; standalone checkout не должен требовать соседних исходников для установки.

## Tailwind и владение CSS

Tailwind 4 и @tailwindcss/vite установлены как devDependencies: каждый репозиторий собирает свой CSS, в federation.shared они не входят. Поддерживаются Chrome 111+, Safari 16.4+ и Firefox 128+.

Файл src/app/styles/page-reset.css подключает reset UI-пакета и импортируется только из main.tsx. Файл src/app/styles/tailwind.css сканирует только собственный src и использует префикс `cart:`: например, `cart:flex`, `cart:hover:bg-blue-600`. Записывайте классы целиком, не собирайте имена интерполяцией. Исходники соседей и UI-пакета не сканируются.

Exposed-компонент импортирует Tailwind и remote.css, поэтому стили доступны и внутри Shell. Reset @microfronts/ui/reset.css импортируется только в src/main.tsx для standalone и не входит в граф exposed-модуля. Глобальные стили страницы остаются в standalone.css.

UI-пакет 0.2.0-tailwind.0 из vendor автоматически поставляет готовые стили компонентов без Preflight и глобальных правил base. Его reset.css содержит Preflight и базовые правила темы. Во всех сборках порядок слоёв: theme, base, components, utilities. Префиксы не изолируют произвольный CSS: ручные правила ограничивайте корнем remote или CSS Modules. Оставшиеся правила без слоя имеют приоритет над utilities; при миграции удаляйте заменённые декларации.

Порядок выпуска: сначала Shell с явным reset, затем remote с CSS без reset. Архивы vendor и lock-файлы обновляются вместе; зависимости на соседние checkout не добавляются.

## Импорты и ESLint

Алиас `@/` ведёт только в собственный `src/`. Он согласован в `tsconfig.json` (paths) и `vite.config.ts` (resolve.alias); Playwright использует конфигурацию проекта и Vite. Зависимости соседних checkout через алиасы не подключаются.

- Между слайсами и слоями: `import { Product } from "@/entities/product"`; внешний потребитель использует только публичный `index.ts` слайса, без глубокого пути и явного `/index`.
- Внутри слайса: прямой относительный путь, например `../model/product`; собственный публичный `index.ts` импортировать нельзя. Реэкспорты из `index.ts` используют относительные пути.
- `app` не имеет слайсов: внутри него разрешены прямые относительные импорты между сегментами. `shared` разделён на сегменты: внутри сегмента пути относительные, между сегментами — через `@/`. Глубокие пути в `shared` разрешены; общий barrel всего слоя не создаётся.
- Зависимости направлены вниз: app → pages → widgets → features → entities → shared. Слайсы одного слоя изолированы. Между сегментами shared разрешены зависимости; локальные исходники за пределами src запрещены. Исключения `@x` сейчас не настроены.
- Правило распространяется на статические импорты, `import type`, реэкспорты, `import()`, TypeScript import types и `require`. Вычисляемые пути модулей и template literals в `import()`/`require()` запрещены: использовать строковый литерал. Строки URL, пути Federation exposes, конфигурация сборщика, CSS `@import`/`@source` и `new URL(..., import.meta.url)` не являются импортами модулей и не переписываются; CSS-импорты из TS проверяются.

`eslint.config.mjs` подключает готовый [eslint-plugin-boundaries](https://www.jsboundaries.dev/docs/) и `eslint-import-resolver-typescript` с собственным tsconfig.json. FSD описана элементами/файлами и декларативными policies: `boundaries/dependencies` проверяет направление слоёв, изоляцию слайсов, публичные API, формат путей и собственный index.ts; `no-unknown-files`, `no-unknown-dependencies` и `no-ignored-dependencies` запрещают неклассифицированные файлы и зависимости. Стандартное правило ESLint `no-restricted-syntax` запрещает вычисляемые пути и исходники без сегмента. Собственных правил ESLint, обхода AST и скрипта проверки архитектуры нет.

`npm run lint` запускается с нулевым допуском предупреждений; `npm run check:architecture` — совместимый псевдоним той же команды. `npm run test:lint` выполняет 10 проверок конфигурации из `scripts/eslint/config.test.mjs`: они загружают реальный eslint.config.mjs и проверяют соглашения проекта на временных примерах, не тестируя реализацию стороннего плагина. Обе команды обязательны в CI до typecheck и сборки. TypeScript import types и import-equals добавлены через штатные additional-dependency-nodes.

Lint контролирует граф разрешённых импортов и классификацию файлов. Наличие index.ts у ещё не используемого слайса отдельно не проверяется; импорт отсутствующего публичного API отклоняется resolver/проверкой неизвестных зависимостей. TypeScript проверяет типы, Vite — сборку; lint их не заменяет.

Cart пока не завершил миграцию на FSD. В `eslint.config.mjs` явно перечислены шесть существующих legacy-файлов: `main.tsx`, `CartApp.tsx`, `api.ts`, `models.ts`, `cart-key.ts`, `remote-props.ts`. Их взаимные импорты и зависимости от FSD используют `@/`. Это временный baseline, а не общее исключение для `src/**`: новые корневые файлы и зависимости новых FSD-модулей от legacy запрещены. При переносе ответственности удалять соответствующий файл из списка. Полная миграция корзины выполняется отдельно; HTTP API и контракт CartProps не меняются.
